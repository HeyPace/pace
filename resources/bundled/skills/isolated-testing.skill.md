## Steps

1. Establish the requested outcome, relevant inputs and apps, and what would make the work finished. Reuse the conversation and existing authorization; ask only for information necessary to proceed. Identify whether the outcome is a file, an external action, or the workspace itself. Let the user's goal determine the workflow. Research, editing a document, converting files, operating an app, building something, and testing are all possible tasks. Do not turn an ordinary task into a testing project or require a repository, source revision, or test suite when those are irrelevant.
2. Use the configured pace-isolated-testing MCP server and its live schemas. Create one task-owned macOS VM with create_space using on=local, image=macos, kind=vm, runtime=lume, reuse=false, count=1, and wait=false. Record its local worker ID and use list_spaces to establish readiness. Provisioning can take time; report starting or blocked accurately. Keep the connection alive during provisioning. Never substitute the owner's desktop when the guest is unavailable.
3. Give the worker only the inputs needed for this task. Public resources can be retrieved inside the guest. For selected local files, use an authorized file tool to stage individual files or a sanitized archive under ~/Library/Application Support/Pace/testing/inputs/<task>/, then send_file and verify its returned hashes. The guard refuses other upload roots and folder uploads. Exclude credentials, environment files, signing material, personal app data, build caches, and unrelated files. Guest accounts and permissions are separate; do not copy the owner's browser profile or sign-ins. If required access is missing, state the specific blocker.
4. Do the requested work in the guest. Discover the available app, browser, filesystem, and other guest tools with list_tools, then call_tool using the explicit owned space ID and supplied schema. Prefer supported APIs or semantic accessibility actions where they fit. Observe fresh guest state, act, and check the effect before continuing. After uncertain delivery, inspect existing state before repeating an action, especially a save, submission, or other mutation. Preserve the user's scope for external actions and publication.
5. Use space_job with action=start for commands that may outlast a short MCP call: downloads, conversions, processing, builds, tests, or other long work. Record the worker, job ID, command, working directory, and timeout. Read status or incremental logs using returned offsets, bounded output, and follow_ms no greater than 5000. A starting job is not a finished task. On an uncertain timeout inspect the existing job before retrying. Preserve running work and report resumable IDs if the turn ends.
6. Verify the user's actual outcome. Reopen or inspect the edited file, check the app-owned saved state, validate the requested conversion, or check the requested action's resulting state. Run only checks that support this task's definition of done. For software work, follow repository instructions and authoritative build/test tools, including XcodeBuildMCP where required; record the source identity and actual executed test counts when applicable. Keep build success, GUI behavior, visual review, and real-hardware behavior distinct.
7. Deliver the finished work. Download selected deliverables into ~/Library/Application Support/Pace/testing/results/ and verify transfer results; the guard supplies a worker subfolder by default and refuses other host destinations. Do not leave the only usable copy in a disposable worker. If the workspace or its configured app state is itself the requested result, retain it and provide its ID and how to continue; do not force a file export. When useful, write a concise task report with space_write and download it alongside the deliverables. Include logs, screenshots, or test results when they help establish the outcome or explain a failure; a test report is not a substitute for the requested work.
8. Return the outcome first: completed, partially completed, blocked, or still running. Say what was accomplished and provide the deliverables or their local paths. Include the evidence needed to trust the result, remaining gaps, and the most useful next action. For unfinished work include worker/job IDs and current state so it can resume. Speak a short result and keep detailed evidence in the text response. Include test counts only when tests were actually relevant and executed. Do not infer 24/7 reliability, universal security isolation, performance improvement, or hardware parity from a short run.
9. Once deliverables are safely collected and no work remains active, delete only a worker that is actually disposable. Never delete app state or a configured workspace that constitutes the requested outcome. Retain an active worker, unrecovered work, or a workspace the owner asked to keep. Never operate or remove another task's worker.

## Notes

This is Pace's general isolated-computer power. Cua provides execution tools; the selected Pace planner supplies reasoning. Use it for tasks that benefit from a separate desktop, or when the owner explicitly asks Pace to use its own computer. Ordinary knowledge answers do not require a VM. Keep existing action approval, provider consent, audit, and cancellation behavior intact.

The existing skill slug, MCP server key pace-isolated-testing, and Pace/testing transfer paths are retained for compatibility. They do not restrict the task to testing. Use only the configured server's supplied tool names and arguments.

The guard reserves unique worker names under Pace's owner namespace before provisioning so reconnects can recover owned attempts. Unknown workers are refused. Every guest operation must identify its owned local space. Never select host, direct addresses, remote/cloud placement, or an inherited shared CLI desktop target. Do not use native host click/type/open-app actions, Peekaboo host control, or the owner's screen as guest evidence. If the owner explicitly chooses a host surface instead, handle that as a separate host workflow and describe its scope accurately. A Mac supports at most two simultaneous macOS VMs; preserve other work and wait for capacity.

Pace's generic MCP result path consumes text and structuredContent. Image-only output does not prove the planner inspected an image. Save useful screenshot artifacts, but mark pixel-only visual review unverified unless an authorized image-capable path examined the guest image. Never present a host screenshot as a guest screenshot.

If Pace itself is under test, retain the leanring-buddy project/scheme names and use scripts/test-pace.sh for isolated unit builds. Hardware, microphone, speech, audio routing, calendar permissions, and TCC continuity need their own evidence.

Long jobs can outlive a tool call. Preserve their IDs and unfinished workspace rather than calling them completed. Cua notifications do not prove Pace received a completion event; report delivery only when observed.
